# 客户版旅游攻略定制

把用户的旅行需求转化为可直接发送给客户的中文攻略成品。目标是延续用户已确认成品的视觉与写作习惯，并给出能落地执行的路线、餐饮、住宿与提醒；不要输出内部风险报告。

## 开始前必读

1. 完整阅读 [references/guide-standards.md](references/guide-standards.md)。
2. 创建或修改 Word 时，同时使用 `documents:documents` Skill，并完整阅读 [references/template-profile.md](references/template-profile.md)。
3. 完整阅读 [references/case-library.md](references/case-library.md)，并在本次任务中读取所有用户提供或保留的案例文档。
4. 完整新攻略、餐厅新增/替换或用户要求餐饮推荐时，完整阅读 [references/restaurant-research.md](references/restaurant-research.md)，并保留内部证据表；该表不交付客户。
5. 新制作完整攻略且找到同城成品参考时，完整阅读 [references/block-reuse-contract.md](references/block-reuse-contract.md)，并在工作目录建立其中规定的内部复用合同；该文件不交付客户。
6. 不设唯一默认模板：先按目的地类型、天数、交通方式、同行人、信息密度与用户当次要求选择最贴合的案例组合；如需复制某一份文档作为工作底稿，只能在副本中编辑，不得覆盖原件。

## 先判定工作模式

开始前只选择一种模式，不能把两种模式混在同一次执行中：

- **完整新攻略：**用户要求从零制作一份完整成品，或现有文件只提供需求而不承担正文底稿。找到同城成品参考时，必须执行内容块复用合同，以最相似同城成品副本为母版，通过保留、删除、复制、移动和组合原内容块完成；禁止清空正文后整体重写。
- **局部修改或重新排列：**用户明确要求续写、补充、替换、重新排序或只修改指定部分。只处理用户指定范围，保留现有局部修改流程；除非用户明确要求整份统一，不因完整新攻略规则扩大修改范围。

## 同城市成品优先检查

每一次定制攻略时，先确定本次目的地城市，并在当前工作目录及可访问的案例目录中查找名为`（城市）旅游攻略成品参考`的文件夹；同时兼容已有的`（城市）攻略成品参考`简称。此检查必须早于路线编写和 Word 制作。

- 没有对应文件夹：继续执行原有需求确认、研究、写作、排版和验证流程。
- 找到对应文件夹：完整读取其中全部成品攻略，按交通方式、天数、同行人、核心景点、酒店片区、天气/季节和游玩类型选择最相近的一份主案例；只有主案例缺少所需内容时，才从其他同城案例补充。不得以文件最新为默认选择理由。
- 完整新攻略先写“景点/体验 → 用餐 → 景点/体验”的行程大纲，再逐项寻找预约说明、景点介绍、时间段、内部路线、相关原图、紧邻餐厅和必要 `Tips：`组成的连续内容块。同城成品中的匹配内容必须整块原样复用，不为换一种说法而重写。
- 原文与行程只因本次酒店位置、到离时间和作息偏好不同而调整，或因闭馆、天气、预约、交通管制、停运、餐厅歇业等动态因素更新。用户明确要求的景点、天数、同行人和交通方式仍必须落实。
- 可修改范围仅限日期、时间、酒店起终点、交通、天气、最新预约与票价、营业状态和用户本次明确要求。其余句子逐字保留；只在内容块之间补最短衔接。找不到同城覆盖内容时才原创，并在复用合同中说明原因。
- 新增且案例未覆盖的内容按本 Skill 原有规则研究和撰写，并把语气、信息密度、标题、图片节奏与同城成品统一；全文保持详细、自然且可直接执行。
- 原推荐餐厅和动态信息必须按餐厅研究规则复核本地评论证据、当前营业状态、准确分店、位置和路线适配性；失效、绕路或证据明显不足的内容不能照抄。仍适用时保持原文的餐厅名称、顺序和简短写法；替换或新增时也沿用主案例的句式与颗粒度。不得复用水印、Logo、个人信息、订单信息或与新行程无关的图片。

## 决策优先级

按以下顺序解决冲突：

1. 用户本次明确要求；
2. 对应城市成品参考文件夹中的用户确认案例；
3. 用户其他全部确认的历史案例；根据与本次任务的匹配度综合取用，而不是把最近一份或单一案例机械套用；
4. `references/template-profile.md`；
5. `references/guide-standards.md`；
6. 默认模板与通用旅行规划惯例。

用户明确要求全程打车、不坐地铁、晚起、少走路或不换酒店时，直接覆盖默认交通或作息偏好。

完整新攻略默认制作成可直接交付的图文 Word；用户明确要求纯文字时才关闭配图。存在同城市成品参考文件夹时优先复用与新行程对应的成品原图；没有同城参考时，使用来源可核验、可合法使用且与正文直接对应的景点图、必要路线图或酒店/交通截图。餐厅评论与 IP 截图只用于内部研究，不进入客户成品。任何模式都不得复用水印、Logo、个人信息、订单信息、无关背景图或页眉页脚图片。

## 工作流程

### 0. 检查同城市成品参考

先执行“同城市成品优先检查”，记录是否存在同城参考目录、目录内全部成品清单、按相似度选出的主案例，以及可直接复用的原文、原图和原推荐餐厅。完整新攻略还必须完成行程大纲和内容块复用合同。未完成这一步，不开始编写。

### 1. 确认需求

确认目的地、日期和固定到离时间、同行人及体力、偏好与必去项、交通和作息、住宿、预算与饮食、预约限制、最终输出格式。不要重复询问用户已经提供的信息；只有缺失信息会实质改变路线时才追问。

### 2. 核查动态信息

对出行日期对应的天气、场馆开放日、预约规则、票价、儿童/老人政策、交通耗时、餐厅评论证据与营业状态进行在线核查。

- 优先官方场馆、政府、运营方、酒店或餐厅页面。
- 无法确认的动态信息写“以出行前官方平台/当天导航为准”，不伪造确定值。
- 保留核查来源供内部验证，不默认把完整链接堆入客户正文。

### 3. 组织轻松且顺路的日程

按片区与实际动线减少折返，并根据老人、儿童、天气、行李和作息安排午休、室内外顺序和步行强度。每一天通常保留 5–7 个主要时间段；只有赶车、预约、演出、索道等硬时间才细分。

除到达日、返程日或用户明确要求省略外，每日时间轴从“起床、洗漱、早餐”开始，不要默认早餐已经完成。远郊、热门预约或必须上午完成的核心项目，应先从预约入场时间倒推路程、堵车/停车、步行和安检缓冲，再决定起床与早餐时间；不能为了补写早餐而挤掉到达缓冲。

每个核心项目写清：为什么值得去、先后顺序和大致停留、到达与转场时间、容易累或需预约的关键点，以及 1–2 个客户能感知的亮点。

### 4. 研究并匹配具体餐厅与交通

先按每日路线确定早餐、午餐、晚餐或夜宵的用餐窗口，再按 [references/restaurant-research.md](references/restaurant-research.md) 执行：从抖音、小红书等平台的相关内容中寻找目的地对应省级 IP 的实质评论，跨帖子交叉验证并排除团购、探店广告、复制文案和商家自荐；提取具体店名后，再用地图或商户官方信息核验准确分店、当前营业状态、时间与路线距离。IP 属地只能作为证据之一，不能单独证明评论者身份。

每个主要用餐窗口通常给 2—4 个顺路的具体选择；远郊或可靠候选少时给 1—3 个。优先控制在前后景点步行约 10—15 分钟或短途接驳范围，不为普通一餐增加明显绕行。同城参考里的原餐厅也必须重新核验：仍适用就保留原句和顺序，失效、明显绕路或证据不足时只替换相应店名，并保持原句结构。菜品只写评论反复出现且当前菜单可确认的 1—3 项，不编造口味和点单建议。客户正文不展示用户名、评论截图、IP 证据或抓取过程。

研究后仍无可靠候选时，优先把用餐窗口调整到当天最近的已核验餐饮聚集区；确实无法核验才说明暂无可靠具体推荐，不用虚构店名或大量写“附近解决”。每段打车或自驾写参考耗时，并对天气、节假日或拥堵保留合理缓冲。

### 5. 编写客户正文

使用自然、直接、有判断的中文。优先短标题、短段落、短列表、`Tips：`、日期和时间标记；不要把核查过程、低概率预案、团队分工或反复的风险提醒写进正文。客户版正文所有文字段落末尾都不写中文句号`。`或英文句号`.`；仅移除段末句号，不改小数点、网址或段落内部正常标点。

没有同城成品参考时，标题不计入部分数量，正文按此顺序默认为四到五个一级部分：`景点预约指南 → 天气指南和穿着携带建议 → 特殊注意事项（可选） → 景点介绍 → 具体行程`。有同城成品参考时，主案例的章节名称、顺序和层级优先；预约、天气、穿着携带、特殊注意事项和景点介绍等前置章节必须直接复用参考文档原文，只微调日期、时间、酒店、交通、天气、最新预约/票价、营业状态和用户明确要求，不得扩写、概括、解释或换一种说法。一级部分使用编号时必须连续。酒店、机场/车站到酒店、跨城交通、酒店周边早餐晚餐、预算等辅助内容按需要放入主案例最相近的位置。

完整成品的每个常规游玩日应形成“起床早餐—前往景点—上午游览—午餐—午休/轻松转场—下午游览—晚餐/夜间体验—返回酒店”的可执行链条。根据目的地和客户偏好，补充真正有用的拍照点、演出、夜游、市场、商圈、酒吧或购物信息，不机械塞满所有模块。

“景点介绍”只写“具体行程”实际安排的景点，按景点在具体行程中第一次出现的顺序排列，每个景点只介绍一次。每项通常写 2–4 句，从历史渊源、名称由来、人物或民间小故事、有趣轶事、文化意义中选择 1–2 项简要介绍；不写成长篇百科，不重复预约、交通、游览路线或注意事项。

日期标题优先只写 `📅 月日`；时间标题使用“时间 + 动作”，例如“参观西安博物院”“前往大明宫”“在某片区吃午餐”。除非确有导航价值，不增加“今日主线”“安排原则”“本版本重点”等方案说明。

时间段的首选写法是“时间点后直接接流程”：写清从哪里出发、怎样到达、景点/小景点顺序、重点看什么、建议停留、何时离开或如何转场。它适合连续、顺路、步骤明确的游览段。若一个时段包含多个相对独立的景点、预约项目、餐饮选择或信息较密集，可在时间点后使用简短小标题、分点或独立段落帮助扫读；小标题必须有实际导航价值，不能只是重复时间点或景点名。根据案例风格和本次行程选择最清楚、最自然的写法，不机械套格式。

景点内部信息采用“建议路线 + 2–3 个重点 + 1 条必要 Tips”的颗粒度。保留能直接照着走的顺序、代表性看点和合理停留时间；删除为路线反复辩护、重复解释取舍或连续罗列低概率风险的段落。

### 6. 生成 Word

先从全部案例中提炼共同的品牌、实用性、信息密度和阅读节奏，再选择与本次行程最贴近的排版结构。存在同城市成品参考文件夹时，必须复制最接近的同城成品作为工作母版，并在副本内保留、删除、复制、移动和组合连续内容块；不要把黄山、苏锡沪、福州或其他任一跨城市案例当成永久唯一模板。

完整新攻略有同城参考时，禁止把主案例正文全部清空后重新生成所有段落，也禁止只保留样式、主题或图片再另写正文。复制内容块时应保留段落与运行级格式、图片关系、裁切、相对位置、标题层级和相邻餐饮内容；跨文档补充块统一到主案例视觉样式，但不改写原句。

- 有同城市成品参考时，优先复用其中仍适用的原文、原图、餐厅推荐、标题结构、时间段组织和信息颗粒度；多个案例拼接后必须统一字体、颜色、标题、段落间距与图片尺寸。
- 没有同城市成品参考时，有多城、亲子、自驾、三代、城市文化游等相近案例可借鉴其标题结构、时间段组织、图文节奏和信息颗粒度，但不得复制跨城市正文或图片。
- 保留用户案例中共有的非图片品牌配色、字体、边框、可直接执行的表达、自然的短段落与非商务表格化倾向；留白和分隔线按匹配案例及当次需求弹性决定。无论模板或历史案例是否带水印，最终成品都不得复制、保留或重新生成任何水印；水印由用户自行添加。
- 不为“统一”而强行改成绿金卡片、纯黑白、彩色时间轴或任何单一风格；同城成品可复用与新行程相符的正文、图片和路线素材，跨城市案例不得复制旧目的地正文、旧图片或旧行程信息。
- 完整新攻略默认图文交付。存在同城市成品参考时，优先复用与相应景点、餐厅、酒店或体验段落直接对应的原图，尽量保留清晰度、裁切和相对位置；没有同城参考或案例缺图时，再补来源可核验、可合法使用且能帮助决策的景点图、路线图或必要截图。用户明确要求纯文字时不配图。
- 图片紧跟对应段落，保持成品案例约每 1—2 页出现一组有用视觉信息的阅读节奏，但以内容需要为准，不为凑数加入无关图。平台评论、IP 属地和个人账号截图不得进入成品。所有图片统一对齐、留白和替代文字。
- 最终文件另存为描述清晰的新文件名。

### 7. 验证

没有同城参考时，先检查正文是否包含默认四到五个一级部分；有同城参考时，检查章节结构是否服从主案例。两种模式都要确认预约、天气、必要特殊提醒、景点介绍和具体行程齐全，编号连续，景点介绍与每日行程的景点集合和先后顺序一致。再做客户 30 秒测试：打开文档后，应能迅速看出去哪、几时开始、主要看什么、吃什么、住哪里。

完整新攻略有同城参考时，逐项对照内容块复用合同：每个在同城案例中找到匹配内容的行程槽位，都必须保留可识别的完整原段落或原句、相关原图及紧邻餐饮/`Tips：`；无必要修改的句子应逐字相同。运行 `scripts/reference_fidelity_audit.py`；如果复用了同城图片却没有任何完整同城段落保持不变，或合同中的复用槽位缺少足够的原段落/原句命中，视为失败，必须恢复原内容块后再交付。

然后做三组交叉检查：

1. `预约场次 ↔ 计划到馆/入馆时间 ↔ 门到门交通与安检缓冲`，三者必须一致；
2. `起点 ↔ 线路号/方向/换乘 ↔ 终点入口`，不得用错误换乘理由推荐交通；
3. `每日起床早餐 ↔ 出发 ↔ 游玩 ↔ 用餐午休 ↔ 回酒店`，不得出现重叠、倒置或没有余量的时间段。

最后检查日期与到离时间、步行强度、每个主要用餐窗口的具体餐厅、准确分店、营业状态与路线距离，确认内部餐厅证据表完整；同时检查天气查询与复核日期、文字准确性、品牌配色和版面密度。图文成品逐图检查与正文对应关系、来源可用性、清晰度、裁切、位置和隐私信息；纯文字成品确认正文、背景、页眉页脚中不存在多余图片。所有成品均不得包含水印。统一日期标题、连续章节编号、时间格式、emoji 前后空格和段落样式；普通说明不得误套时间标题样式。完成错别字、店名、分店名、站名、线路号、方向和时间范围的纯文字校对。使用 `render_docx.py` 渲染全页并逐页检查；无 Word/LibreOffice 时完成结构化检查，并如实说明未能逐页渲染。

## 交付

默认交付一份可直接发送给客户的图文 Word 成品，并提供最终文件链接。同城市成品参考存在时，按上述规则复用适用原文、原图和经重新核验的餐厅；不存在时按最相近成品的结构与图文节奏原创。用户明确要求纯文字时遵从。只在确实影响使用时简短说明限制。
